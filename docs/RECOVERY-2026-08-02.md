# Recovery — home directory wipe, 2026-08-02

Written 2026-08-03 from forensic inspection of the live machine (journal, apt/dpkg
logs, filesystem timestamps). Everything in "What happened" is evidence-backed;
the cause section states plainly what could and could not be established.

## What happened

The machine ran normally all day. Between **17:38 and 17:41 PDT on 2026-08-02**,
something deleted most of the dot-directories in `/home/potter`. No reboot, no
crash, no package operation.

```
Aug 02 17:10:32  dg-tab-hygiene: "before": 3, "closed": 0, "kept": 3   ← Chrome alive over CDP
Aug 02 17:38:11  demigod-events-heal ... Finished                      ← last healthy tick
Aug 02 17:40:47  cosmic_files: failed to read directory /home/potter/Desktop/: No such file or directory
Aug 02 17:40:57  cosmic-panel: Failed to get entry value: GetKey("padding_overlap", ... NotFound)
Aug 02 17:40:57  cosmic-comp: Failed to read config 'xkb_config'
Aug 02 17:40:59  dbus-broker-launch: Noticed file-system modification, trigger reload
Aug 02 17:43:14  sudo: potter : a password is required ; PWD=/ ; USER=root ; COMMAND=/usr/bin/true
```

That last line is a process sitting in `/` probing for passwordless root and
being denied. It is why the damage stopped at `$HOME` and `/usr` survived.

### Ruled out

| Hypothesis | Evidence against |
|---|---|
| Disk full / hardware | 27G used of 929G, 1% inodes, no I/O errors, ext4 from 2023-08-28 intact |
| OS reinstall / Pop!_OS refresh | `/`, `/usr`, `/var` date to 2023; apt+dpkg logs continuous since 2023; unbroken boot history |
| Package uninstall | Zero removals in apt history. Only nearby transaction is the user's own `apt install npm` on 2026-08-03 13:15 |
| Accidental trash | `~/.local/share/Trash` does not exist — files were unlinked directly |

### Destroyed

All dot-directories and dot-files, plus `~/Desktop`:

- `~/.config/*` — COSMIC desktop settings, **`~/.config/systemd/user/`** (all agent units), `~/.config/gh`
- `~/.local/*` — every user-installed CLI binary
- `~/.var/` and `~/.local/share/flatpak` — **Chrome was a Flatpak user install**; app and profile both gone
- `~/.nvm` (node v24.17.0), `~/.bun` (bun 1.3.14)
- `~/.gitconfig`, `~/.profile`, `~/.bash_profile`, `~/.bash_logout`, real `~/.bashrc`, `~/.bash_history`
- `~/.codex`, the home repo's original `.git`, and any `.env` secrets

### Survived

Every non-dot file in `/home/potter` — the entire demigod project tree, ~1000
files, still carrying 2026-08-02 04:54 mtimes. **No project work was lost.**
That includes `bin/`, `systemd-user/`, and all `demigod-*.mjs`.

## Cause

Not determinable, and here is why: the logs that would identify the process were
themselves inside the deleted set — `~/.codex` session history, `~/.bash_history`,
and the old `.git` reflog. Linux does not log file deletions, so the journal
records only the aftermath.

What the evidence supports: a process running as `potter`, working directory `/`,
performing a recursive delete scoped to dot-entries in `$HOME`, which then checked
for root escalation. Two unattended agents were running through the window — a
Codex session, and `demigod-useful-loop.service` (`Restart=always`, plan→do→verify).
Either fits. No basis to choose between them.

**Structural hazard.** `$HOME` is a git repo, and `.gitignore` hard-ignores
`.config/`, `.local/`, `.cache/`, `.var/`, `.nvm/`, `.bun/`, `.codex/`, `.claude/`,
`.grok/`. Any agent running a cleanup in `~` — `git clean -xfd` being the obvious
candidate — deletes precisely that set and leaves tracked project files pristine.
That is exactly the observed damage pattern. The `.gitignore` header already flags
home-as-repo as a known danger.

### Toolchain regression — do this first

`apt install npm` on 2026-08-03 installed **Ubuntu's node 18.19.1 / npm 9.2.0**.
The pre-incident toolchain was **node v24.17.0 / npm 11.13.0 via nvm**, and
`systemd-user/demigod-useful-loop.service` hardcodes:

```
ExecStart=/home/potter/.nvm/versions/node/v24.17.0/bin/node /home/potter/demigod-useful-loop.mjs ...
```

That path does not exist. The agent units will not start until nvm + node 24.17.0
are reinstalled. Install nvm from <https://github.com/nvm-sh/nvm>, then:

```bash
nvm install 24.17.0 && nvm alias default 24.17.0
```

### Agent units

Definitions survived in `~/systemd-user/` (22 units). The installed copies in

```bash

ln -sf ~/systemd-user/*.service ~/systemd-user/*.timer ~/.config/systemd/user/

```

Enable them **deliberately, one at a time**. `demigod-useful-loop.service` was
running unattended during the wipe and is one of the two candidate causes; do not
re-enable it with `Restart=always` until the home-as-repo hazard below is fixed.

## Recovery of lost data

- **No backups exist.** No Timeshift, no `/.snapshots`, no second drive, no Trash.
- The deleted config and credentials are realistically unrecoverable. The
  filesystem has been written to heavily since; ext4 undelete is not viable.
- One live lead: remote `https://github.com/Uuriko/demigod-ops.git`. If it holds
  pre-2026-08-02 history it is the best restore point for anything the current
  snapshot lost. Requires re-auth to check.

## Prevention

1. **Move the repo out of `$HOME`.** This is the fix that matters. As long as the
   working tree is `/home/potter`, any `git clean -xfd` — by an agent, a script, or
   a stray paste — deletes every ignored dot-directory on the machine. Relocating
   to `~/src/demigod` makes the same command harmless.
2. Set up a backup with history before re-enabling autonomous loops.
3. Install agent CLIs system-wide rather than under `~/.local`.
4. Keep unattended loops out of `$HOME` as working directory.
